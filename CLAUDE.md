# MacPad++

A native macOS port of Notepad++ (v8.9.8.1). Goal: behave like the Windows Notepad++ the user
knows, but as a real Mac app — not Wine (tried, rejected as terrible), not a loose clone.

## Decisions (agreed with the user on 2026-10-13)

- **UI:** Swift + AppKit. Native menu bar, Cmd shortcuts, dark mode, Finder "Open With".
- **Editor engine:** Scintilla's Cocoa backend (`ScintillaView`) + Lexilla — the same engine
  Notepad++ uses, so editing/folding/multi-caret/column mode/lexers behave identically.
- **Data files reused verbatim from Notepad++:** `langs.model.xml`, `stylers.model.xml`,
  `themes/*.xml`, `functionList/*.xml`, `autoCompletion/*.xml`. Notepad++ user themes must import as-is.
- **Logic:** port non-Win32 C++ from `PowerEditor/src` where it is portable (encoding detection,
  search semantics, session/config formats). Rewrite every Win32 UI piece in AppKit.
- **Out of scope:** Notepad++ plugins (Windows DLLs cannot load on macOS).
- **License:** derived from Notepad++ ⇒ GPLv3. "Notepad++" is Don Ho's name — never brand the
  app with it; the app is **MacPad++**.

## Layout

- `vendor/notepad-plus-plus/` — shallow clone of tag `v8.9.8.1` (gitignored, read-only reference).
  - `scintilla/cocoa/` — ScintillaView, `Scintilla/Scintilla.xcodeproj`, `ScintillaTest/` (sample host app)
  - `lexilla/src/Lexilla/Lexilla.xcodeproj`
  - `PowerEditor/src/` — Notepad++ app code (`ScintillaComponent/`, `WinControls/`, `Parameters.cpp`, …)
  - `PowerEditor/src/langs.model.xml`, `stylers.model.xml`; `PowerEditor/installer/{themes,functionList,APIs}`
  - `boostregex/` — Notepad++'s regex engine for Scintilla search (Perl-style regex, used by Find/Replace)
- `scripts/build-deps.sh` — builds `build/deps/Scintilla.framework` + `liblexilla.a` from vendor/.
- `project.yml` — XcodeGen spec (the generated `MacPad++.xcodeproj` is gitignored).
- `MacPad/Sources/` — the app (Swift, AppKit, no nibs). `LanguageTable.swift` is generated from
  Notepad++'s `_langNameInfoArray`; regenerate it rather than editing by hand.
- `MacPad/Resources/Assets.xcassets/AppIcon.appiconset` — app icon PNGs, generated by
  `swift scripts/make-icon.swift` (an original design; never use Notepad++'s chameleon logo).
  Edit the script and regenerate rather than editing the PNGs.
- At build time a script phase copies `langs.model.xml`, `stylers.model.xml` and `themes/` from
  vendor/ into the app's `Resources/npp/`.

## Build

```bash
scripts/build-deps.sh && xcodegen && xcodebuild -project MacPad++.xcodeproj -scheme MacPad++ -derivedDataPath build/dd-app build
```

App: `build/dd-app/Build/Products/Debug/MacPad++.app`.

Tests: `xcodebuild test -project MacPad++.xcodeproj -scheme MacPad++` (target `MacPad++Tests`; the
app's module is `MacPad`, since `MacPad++` is not a legal Swift module name).

Installer: `scripts/make-pkg.sh` → `dist/MacPad++-<version>.pkg` (tests, Release build, signing,
then `pkgbuild` + `productbuild`; installs into `/Applications`). A `.pkg` is the project's installer
format — not a `.dmg`. The package declares MacPad++ **must-close**: if it is running, Installer asks
to close it before installing (MAC-19). Only the newest installer is kept — the script deletes older
`MacPad++-*.pkg` in the output folder after a successful build (user's rule, 2026-10-13). Note the two identity classes: a Developer ID *Application* certificate signs
the app, a Developer ID *Installer* certificate signs the package.

## Vendor quirks (handled without editing vendor/)

- Lexilla's Xcode project hard-codes signing team 4F446KW87E and omits the three lexers Notepad++
  adds (`LexObjC`, `LexSearchResult`, `LexUser`), so `build-deps.sh` compiles Lexilla directly.
- `LexUser.cxx` includes `<windows.h>` and calls MSVC `_itoa`: a generated shim header covers both.
- Notepad++ appended an unguarded C++ block (`SearchResultMarkings`, `std::vector`) to the public
  `Scintilla.h`. The Swift bridging header is plain ObjC, so `build-deps.sh` wraps it in
  `#ifdef __cplusplus` in the built framework's copy.
- Scintilla.h and other vendor files use CRLF line endings: patterns must allow `\r?\n`.
- Regex search is Notepad++'s Boost engine (MAC-29): `build-deps.sh` builds `boostregex/` into
  `libscintilla-boostregex.a` and links Scintilla with `SCI_OWNREGEX`. On macOS Boost classifies
  `wchar_t` through the "C" locale, where libc++ knows no non-ASCII letters (`\w` missed Hebrew);
  `scripts/deps/BoostRegexLocale.cxx` (force-loaded) installs a UTF-8 `ctype<wchar_t>` facet globally.
  Notepad++'s extra flags (`SCFIND_REGEXP_DOTMATCHESNL`, …) come from `BoostRegexSearch.h`.

## Testing gotchas

- Never drive the app with `osascript ... keystroke` unless MacPad++ is verified frontmost: keys go
  to whatever app has focus (on 2026-10-13 a stray `x` + ⌘S reached the user's Chrome). Use
  `key code` (layout-independent; the user's input source is Hebrew, so `keystroke "x"` types ש)
  and check `frontmost` first. `pkill MacPad++` fails on the `+`; use `pkill -f 'MacPad\+\+\.app/Contents/MacOS'`.
- A Debug build launched by hand shares the installed app's Recent Files and session (same bundle
  id). For manual checks launch it isolated: `open --env MACPAD_ISOLATED_STORAGE=1 -a <app> <file>`
  (tests are isolated automatically — MAC-23). Never quit or drive the user's own running MacPad++.
- With two MacPad++ processes running (same bundle id), System Events' `set frontmost` on the test
  instance can activate the *other* one, and menu clicks then land there (2026-10-14: a test script
  typed into the user's instance). Before any UI scripting, list `pgrep -fl 'MacPad\+\+\.app/Contents/MacOS'`;
  if anything besides the test instance runs, do not script the UI — ask the user first. After
  activating, check `unix id of (first process whose frontmost is true)` equals the test pid.
- Debug builds use the bundle id `app.macpad.MacPad.debug` (Release keeps `app.macpad.MacPad`), so
  Finder / Open With never launches a build-folder copy for the user's files and a Debug build never
  reads the installed app's preferences. Before this, one did (2026-10-14).

## Milestones (each one ends with a working app)

1. **Skeleton** — Scintilla + Lexilla building for arm64; one window, open/save, lexer by file
   extension, Notepad++ default theme from `stylers.model.xml`.
2. **Tabs** — multi-document, session restore, recent files, encoding + EOL in status bar.
3. **Find/Replace** — Normal / Extended / Regex (boostregex), Find in Files, Mark, incremental search.
4. **Language menu, Style Configurator, themes, Preferences.**
5. **Edit commands** — line ops, case, comment toggle, Column Editor, macros, Shortcut Mapper.
6. **Panels** — Function List, Document Map, Folder as Workspace, split view.
7. **Packaging** — signed `.app`, `.pkg` installer, file-type associations.

Milestone 1: **done** (2026-10-13). One window per document; open/save (Finder "Open With" too);
lexer + keywords by extension from `langs.model.xml`; default theme from `stylers.model.xml`; folding,
brace match, Notepad++-style status bar; BOM/UTF-8/UTF-16/ANSI decode + byte-exact save; EOL kept.

Known approximations, to be closed in later milestones:
- Per-language lexer setup (`ScintillaEditView::defineDocType` and its set*Lexer helpers) is the
  table in `LexerRecipes.swift` (MAC-11): keyword sets per language, lexer properties, substyles
  (substyle1…8 = keyword classes 9…16), HTML/PHP/ASP/JSP as "hypertext" with embedded JS/PHP/VBScript
  styles, EOL-filled styles, tabSettings, indent guides, fold margin. Not ported: NFO's Lucida Console
  default and per-language word characters.
- Encoding detection (MAC-10) is Notepad++'s: uchardet (`build/deps/libuchardet.a`, from
  `PowerEditor/src/uchardet`) + EncodingMapper (`CodePageTable.swift`, generated, 46 code pages).
  Differences: valid UTF-8 is accepted before asking uchardet; "ANSI" is Windows-1252 (Notepad++
  uses the system code page), so detected 1252 / ISO 8859-1 show as ANSI; uchardet's KOI8-R and
  ISO-8859-8-I names are mapped (Notepad++'s table misses them). Converting *to* an arbitrary code
  page (Encoding › Character sets menu) is not built yet.
- Font sizes are scaled by 4/3 (Windows 96 dpi points → macOS points) and new files use LF, not
  CRLF — both now Preferences (MAC-12/MAC-38: Misc. › scale font sizes, New Document › Format).
- First-line detection (`LanguageDetector`, MAC-11) follows Notepad++'s detectLanguageFromTextBeginning.

Milestone 2: **done except MAC-25** (2026-10-14, release 0.1.8) — tabs, session restore, recent files,
encoding/EOL pickers, encoding detection, tail -f, reload on external change, Save as Administrator
with Touch ID, window placement. MAC-25 (full security review incl. the GitHub code) is the stage's
last item by the user's choice.

Privileged helper (MAC-24/MAC-28): `MacPadHelper` is installed by the `.pkg` — `scripts/pkg/postinstall`
writes `/Library/LaunchDaemons/app.macpad.MacPad.helper.plist` and bootstraps it (no SMAppService, no
Login Items step). The app pings it over XPC; Touch ID when it answers, the password prompt otherwise.
Only team-96Y4LX7FVB-signed builds pass the code-signing requirements, so Debug builds always use the
password path. Known gap, tracked in MAC-25: the user-presence check is in the app, not the helper.

Milestone 3: **done** (2026-10-14, release 0.1.10) — Notepad++'s Boost regex engine (MAC-29),
Find/Replace dialog (MAC-30), Mark + token styles + bookmarks (MAC-31), Search results panel with
Find All / Replace All in opened documents (MAC-32), Find in Files / Replace in Files (MAC-33),
incremental search and Go To (MAC-34). Mac shortcuts replace Notepad++'s where macOS owns the key:
⌘F / ⌥⌘F / ⇧⌘F / ⇧⌘M for Find / Replace / Find in Files / Mark, ⌘G / ⇧⌘G for F3 / Shift-F3,
⌥⌘I incremental search, ⌘L Go To; F2 / F4 / F7 stay as in Notepad++.
Not ported yet: "Find in these search results…", Line Filter Mode, the regex error detail text.

Milestone 4: **done** (2026-10-14, release 0.1.11) — Language menu (MAC-35, generated from
Notepad_plus.rc by `scripts/gen-language-menu.py`), per-language lexer setup + first-line detection
(MAC-11), theme selection (MAC-36, `ThemeManager`), Style Configurator (MAC-37, `StyleDocument`
patches theme XML in place; Default → user stylers.xml, other themes copied to the user themes
folder), Preferences window ⌘, (MAC-38, `Preferences`, applied live). User files live in
`~/Library/Application Support/MacPad++/` (stylers.xml, themes/). Not ported: UDL, colorStyle
transparency, "Go to settings" links, Print/Backup/Auto-completion pages.

Next: milestone 5 (Edit commands — line ops, case, comment toggle, Column Editor, macros, Shortcut Mapper).

## Process requirements (set by the user on 2026-10-13)

- **Jira:** every item of work gets a ticket in project **MAC** ("macpad++") on the private
  Atlassian site — board https://nachum-shmilovitz.atlassian.net/jira/software/projects/MAC/boards/167.
  Open the ticket before the work starts, close it with a description of what actually shipped.
- **Testing:** every feature ships with full unit-test coverage; every bug fix ships with a
  regression test. Extract logic out of AppKit views where needed so it can be tested headless.
- **Versioning:** the line starts at `0.1.0` (`MARKETING_VERSION` in `project.yml`). At this stage
  every release bumps the **patch** only.
- **`deploy patch`** means, in order: run the unit tests (a failure stops everything) → bump the
  patch → update and close the Jira tickets → commit and push → build the `.pkg` installer into `dist/`
  for every requested platform (currently macOS arm64 only; `.pkg`, never `.dmg`) → ask the user whether to install it.
- **Installing** (when the user says yes): it needs their admin password / Touch ID, so open the `.pkg`
  in Installer (`open dist/MacPad++-<v>.pkg`) for them to confirm — never try `sudo installer`. If
  MacPad++ is running, **ask the user whether to close it** first (it may hold unsaved work); the
  package's must-close prompt asks again in Installer. Never quit it unasked.
